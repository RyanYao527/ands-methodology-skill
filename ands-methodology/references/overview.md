# ANDS Overview

## 定位

ANDS（AI-Native Development System）是组织级 AI 原生研发操作系统：用标准定义协作，用平台承载执行，用方法论保证闭环。它不是单个 AI 编程工具、不是课程大纲，也不是一套必须全量落地的重流程。

核心公式：

```text
人 = 决策 + 验证
AI = 执行 + 辅助分析
知识 = 核心资产
版本 = 五资产同步快照
度量 = 改进证据
```

## 何时读取

- 用户问“ANDS 是什么”“适不适合我们”“和 AI 编程工具有什么区别”。
- 用户需要管理层简报、内部宣讲、一页式解释或采用边界判断。
- 需要在进入具体标准、平台、治理或 demo trace 前统一口径。

## 核心规则/方法

### 三层架构

| 层 | 作用 | v0.1 输出重点 |
|---|---|---|
| Framework | 五大标准，定义组织协作的“宪法” | ANDS-K/T/A/W/G 的最小定义 |
| Platform | 五个组件，承载知识、执行、调度和可视化 | Obsidian、GitHub、Agent、Gateway、Dashboard 的边界 |
| Methodology | 十个模型，说明怎么想、怎么做、怎么改进 | 从研发哲学到度量回写的逻辑链 |

### 与常见体系的区别

| 对象 | ANDS 的差异 |
|---|---|
| 普通 AI 编程工具 | 不只提高个人编码效率，而是定义组织级标准、知识资产和治理闭环 |
| 多 Agent 工作流 | 不只编排 Agent，还要求任务标准、知识回写、Gate 和度量 |
| Spec/Plan/Task 工具链 | 可作为 ANDS-T 到执行拆解的实现方式，但 ANDS 还覆盖知识、版本、治理和组织推广 |
| DORA/SPACE 类度量 | 可借用指标思想，但 ANDS 把度量接入 Gate 5 和标准迭代 |

### 适用边界

适合：

- 团队已经在用 AI 工具，但任务、知识和验收混乱。
- 需要把 AI 协作从个人经验变成团队可复制机制。
- 需要管理者能判断风险、投入、治理强度和推广路径。

不适合：

- 只想临时生成一段代码。
- 没有人愿意承担决策与验收责任。
- 期望 v0.1 直接交付生产级 Gateway、Dashboard 或完整课程。

## 输出口径

管理者输出：

- 先给结论：是否适合、先做什么、风险是什么。
- 使用路线图、决策表、投入估算、治理边界。
- 少讲工具细节，多讲组织机制和知识资产飞轮。

实践者输出：

- 先给可执行模板或清单。
- 明确下一步：写 ANDS-T、建知识域、选 Track、过 Gate、写 Lessons。
- 给出验收标准，不展开课程式背景。

## 输出要求

- 首段必须用一句话解释 ANDS。
- 至少说明“人决策与验证，AI 执行与辅助分析”的边界。
- 不默认推荐完整五道 Gate 或生产级平台。
- 不包含可识别组织、人员、仓库地址、域名、IP、凭据或业务敏感数据。
