# 管理落地示例：20 人研发团队 30 天 ANDS 试点方案

> 对应验收 prompt：我们是一个 20 人研发团队，已经在用 Cursor 和 Codex，但现在比较混乱，没有统一任务标准，也没有知识沉淀。请用 ANDS 给我一个 30 天试点方案。

## 适用性判断

适合启动 30 天 Standard 轨试点，但不适合一开始做完整平台建设。

判断依据：

| 条件 | 当前状态 | 结论 |
|---|---|---|
| 已有 AI 使用基础 | 团队已使用 Cursor 和 Codex | 满足 |
| 主要问题是组织标准缺失 | 任务写法、验收口径、知识沉淀混乱 | 满足 |
| 可选小范围真实需求 | 需要由团队选出 1 个 2-4 周内可闭环需求 | 需确认 |
| 人类验收责任 | 必须指定 Project Owner 和业务验收角色 | 需确认 |

如果没有人愿意承担 Gate 1 需求准入、Gate 3 人验收和 Gate 4 发布审批，先不要启动正式试点。可以先做半天任务标准工作坊，把现有需求改写成 ANDS-T。

## 30 天试点目标

30 天只证明一件事：团队能不能用一条 Standard 轨需求跑通 `ANDS-T -> AI PM 拆解 -> Agent 执行 -> Gate -> Release -> Lessons`。

不把 30 天目标设为：

- 搭建生产级 AI Gateway。
- 建完整 Dashboard。
- 改造所有团队流程。
- 迁移全部历史文档。
- 要求所有任务都走重流程。

## 试点项目选择标准

优先选择：

| 标准 | 要求 |
|---|---|
| 范围 | 1 个小功能、修复或内部流程改进，2-4 周内可交付 |
| 验收 | 有明确业务验收人，能写出 3-5 条业务可验证 Acceptance |
| 风险 | 不处理敏感数据，不在生产关键路径上做不可回滚变更 |
| 上下文 | 至少有需求说明、当前流程说明、相关限制和历史问题记录 |
| 复盘价值 | 能产出 ANDS-T、Gate 记录、五资产快照和 Lessons |

避免选择：

- 需求边界持续变化、多个部门意见无法收敛的项目。
- 没有业务验收人的“探索一下”类任务。
- 一开始就涉及权限、资金、合规、生产迁移或跨系统契约变更的任务。

## 30 天路线

| 时间 | 目标 | 关键动作 | 最小产出 |
|---|---|---|---|
| 第 1-3 天 | 建立试点边界 | 指定 Project Owner、AI PM、业务验收人；选择 1 个 Standard 轨需求 | 试点范围说明、角色分工 |
| 第 4-7 天 | 建立最小标准 | 把需求写成 ANDS-T；建立 8 域知识骨架；明确 Gate 2/3 口径 | ANDS-T 任务卡、知识域索引、Gate Checklist |
| 第 8-14 天 | 跑第一次执行 | AI PM 拆解任务、分配 Agent、列上下文清单；Agent 执行最小交付 | 任务拆解、执行记录、变更摘要 |
| 第 15-21 天 | 完成审查与验收 | Gate 2 做机器质量检查；Gate 3 由人按 Acceptance 验收 | 检查记录、验收记录、返工项 |
| 第 22-26 天 | 发布与快照 | 准备变更说明、回滚口径、五资产快照 | Release 记录、五资产快照 |
| 第 27-30 天 | 复盘和回写 | 写 Lessons，创建改进 Issue，决定是否进入 60 天固化 | Lessons、标准更新建议、下一轮任务 |

## 最小标准

30 天试点只要求 4 类标准落地：

| 标准 | 最小版本 |
|---|---|
| ANDS-T | 每个试点任务有 Goal / Input / Constraint / Output / Acceptance / Track / Gate Requirement |
| ANDS-K | 建立 Vision、Product、Technical、Decision、Prompt、Lessons 等必要知识域，不要求 8 域填满 |
| ANDS-G | Standard 轨默认保留 Gate 1-5，但 Gate 2 和 Gate 3 必须分开 |
| Lessons | 每次返工、延期、No-Go 或成功经验都记录为可回写的 Lesson |

## 角色与责任

| 角色 | 责任 |
|---|---|
| Project Owner | 决定试点范围、批准 Gate 1、参与 Gate 4 |
| AI PM | 拆解任务、分配 Agent、组装上下文、过程质检 |
| 执行 Agent | 按 ANDS-T 和约束完成指定交付物 |
| Validation Agent | 设计或运行 Gate 2 检查，输出失败项 |
| 业务验收角色 | 按 Acceptance 做 Gate 3 人验收 |
| Knowledge Writeback 角色 | 整理 Lessons、双链和改进 Issue |

## 风险与应对

| 风险 | 表现 | 应对 |
|---|---|---|
| 任务写得像普通需求 | Agent 只能猜，交付后返工 | Gate 1 不通过，补齐 Input、Constraint、Acceptance |
| 治理被理解为加流程 | 团队抵触 Gate | 用 Track 裁剪，Quick 任务保留必要机器检查和红线 |
| Acceptance 混入工程项 | 业务验收人不知道如何验收 | 把测试、lint、构建移到 Gate 2，Acceptance 只写业务结果 |
| 知识没有回写 | 下次任务仍然从聊天记录开始 | Gate 5 不通过时不得关闭试点任务 |
| 试点范围扩大 | 30 天无法闭环 | Project Owner 在 Gate 1 重新裁剪范围或升级 Track |

## Gate 5 回写

试点完成后，至少写回这些知识：

| 回写对象 | 内容 |
|---|---|
| Product | 试点需求、验收口径、用户反馈 |
| Technical | 执行约束、检查命令、质量证据摘要 |
| Prompt | 可复用的 AI PM 拆解 prompt、Agent 执行约束 |
| Decision | Track 选择、范围裁剪、发布或不发布决策 |
| Lessons | 返工、延期、验收偏差、Gate 失败和改进 Issue |

30 天结束的管理判断不是“AI 写了多少代码”，而是团队是否形成了可复用的任务标准、验收机制和知识回写闭环。
